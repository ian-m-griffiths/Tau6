# Tau RISC-V — status & handoff

**2026-08-29.** Where the project stands after the Phase 0–3 software, the Phase 4 RTL
hex address unit, the Phase 5 field-calculus proofs, and the Phase 6 SoC assembly. Every
artifact below was re-verified green this session.

## The thesis (one line)

A **binary RISC-V core** with a **ternary/hex memory subsystem** (Eisenstein ℤ[ω]
addressing, the `3ⁿ` namespace) and **ternary transport**, plus an **Xlattice**
geometric-algebra co-processor. Compute stays binary (the ALU is where ternary *loses*
1.26–3.5×/bit); ternary wins in **addressing** (exponential) and **transport** (~2.7–6.3×).

## The SoC (`rtl/tau_soc.v`) — now assembled and green

A real RV32I program runs on **PicoRV32** and drives **four** ternary subsystems through
memory-mapped peripherals, all in one iverilog simulation:

| peripheral | base | what it does | status |
|---|---|---|---|
| hex MMU | `0x1000` | isotropic 7-cell pod lookup (`hex_pod_addr`) | PASS |
| field accelerator | `0x2000` | **TGRAD** (div/curl), **TRECON** (gauge-fixed ∇⁻¹), **TRELAX** (heat step) | PASS |
| ternary transport link | `0x3000` | null-count + 11=NEVER canary + transport energy (centi-pJ) | PASS |
| Xlattice co-processor | PCPI custom-0 | TDOT/TWEDGE/… GA ops on the CFU port | PASS |

The test program (`rtl/program_tau.hex`, generated by `scripts/gen_program_tau.py`) exercises
all four: it writes a field `F0=+3, F1=+9` on `pod(6)`, reads back **div=+3, curl=+9**, runs
the **TRECON** round trip (reconstruction == original, overflow flag clear), steps **TRELAX**
(center `6 → +1` = `sum/9`), and puts an all-null word and a one-active word on the **ternary
link** (12 nulls → 60 centi-pJ; 0x010 → 11 nulls, 175 centi-pJ).

```bash
# assemble + simulate the whole SoC (from repo root; do NOT use -g2012)
iverilog -o /tmp/tau_soc.out picorv32/picorv32.v rtl/ternary_gates.v rtl/tmul_opt.v \
  rtl/ga_ops.v rtl/xlattice_cfu.v rtl/picorv32_pcpi_xlattice.v rtl/hex_encode.v \
  rtl/hex_decode.v rtl/hex_pod_addr.v rtl/hex_mmu_periph.v rtl/grad_recon.v rtl/trelax.v \
  rtl/hex_field_accel.v rtl/ternary_link.v rtl/ternary_link_periph.v rtl/tau_soc.v \
  rtl/tau_soc_tb.v && vvp /tmp/tau_soc.out
```

Expected tail: `PASS — the full processor ran TGRAD + TRECON + TRELAX + ternary transport.`

**A real bug was found and fixed this session.** The field accelerator's cell store holds
*balanced-ternary* field values (2 bits/trit), but the first test program wrote *raw binary*
integers (`3 = 2'b11` is the NEVER canary). TGRAD therefore read garbage (`div=1` instead of
`3`). The fix: software encodes field values (`enc(+3)=0x004`, `enc(+9)=0x010`) and the
testbench decodes div/curl back. This is not a dodge — the ternary representation is the
point; addresses (cell indices) stay plain binary, values are the ternary field.

## The honest scoreboard (unchanged, now with artifacts behind it)

| axis | verdict | artifact |
|---|---|---|
| **namespace** | `3ⁿ` vs `2ⁿ` → `(3/2)ⁿ` = 1.86×10¹¹ at n=64 | `TritPacking.lean`, `Bijection.lean`, `NAMESPACE_TABLE.md` |
| **transport** | ~2.7–6.3× win, radix-agnostic, free-null *conditional* | `FINAL_VERDICT.md`, `transport.py`, `rtl/ternary_link_periph.v`, ngspice |
| **compute** | ~1.26–3.5×/bit LOSS (2-threshold tax) | `ThresholdLowerBound.lean`, `FINAL_VERDICT.md` |

**The engine computes on addresses, not bits** — so the compute loss is irrelevant to the
engine's actual workload, and the wins are exactly where the engine lives.

**Axis disambiguation (asked and answered):** transport is **2.7–6.3× BETTER** — a win, never
"worse" (0.081 pJ/bit vs 0.512 natural / 0.216 matched low-swing). The **1.42×/bit** figure is
the mod-3 sum `⊕` — a **compute** gate, a *loss*, on a separate axis; a null-rail design tweak
reduced it from the worse diode-gate 3.4–4.9×. There is nothing to "get back to": the transport
win is unchanged, and 1.42× is the compute loss, not transport.

## Polar / "trinary" memristor — the honest answer

The requested "polar memristor that lets flow in one direction" was surveyed (`docs/riscv_survey/
polar_memristor.md`). **Verdict: a direction-encoded memristor does NOT beat the 2-bit/trit cell
on storage energy/density.** It is another "0.63× native floor" flattery, and worse-evidenced
than the AAT:

- "Polar memristor" in the literature means bipolar/unipolar switching (a 2-state *bit* whose
  write polarity is the sign) or a self-rectifying *selector* for sneak-path suppression — not
  a trit encoded by current direction.
- The only "trinary memristor cell" papers encode by resistance *magnitude* (3-way threshold),
  and report **no** storage energy/density/endurance. The one paper with numbers (TReMo+) shows
  per-cell area ≈ identical to SLC, so the whole ~1.58×/bit density is just the `1/log₂3` factor
  *conditional on a free native cell*, with the 2-threshold tax repriced as write-verification
  energy (12 vs 5 iterations to land the middle state).
- The genuine direction-encoded trit exists (BiFeO₃ ferroelectric diode, APL 2022) but is a
  materials demo with zero endurance/retention/energy numbers.
- **Why direction-encoding doesn't sidestep the tax:** reading it needs a 2-polarity probe plus
  a null-vs-non-null comparison — still two discrimination steps — and the "free null" is a
  *transport* property (the wire carries no current), which does not transfer to a *storage*
  cell that must actively hold and read the null.

Same bottom line as every native device: **real, but loses to / no better than the 2-bit
encoding on the honest axis.** The ternary wins stay where they always were — addressing
(exponential) and transport (free null on the wire) — not storage or compute.

## What remains (optional)

Everything self-contained is built, simulated, and green — the SoC is no longer "the single
remaining step." Genuinely optional next steps, in value order:

1. **TRELAX over a full field** — the accelerator relaxes one center cell per trigger; looping
   it over a region (in software, cell-by-cell) would run a real heat-equation solve on the SoC.
2. **NEORV32 variant** — re-target the same peripherals onto NEORV32's Wishbone bus (the CFU
   adapter `neorv32_cfu_xlattice.v` already matches its real interface).
3. **Synthesis** — map `tau_soc.v` through yosys to get a chip-area number for the whole system,
   not just the ternary CPU datapath.
